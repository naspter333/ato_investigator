# ATO Investigator

A Week 1 Path 3 vibe-coded data application for investigating account takeover. Connect login attempts, password resets, device and country changes, beneficiary additions, and transfers into an explainable account timeline.

## Run locally

Requires Python 3. No pip packages or npm installation are needed to run the app.

```bash
git clone https://github.com/naspter333/ato_investigator.git ato-investigator
cd ato-investigator
python3 -m http.server 8501 --bind 127.0.0.1 --directory dist
```

Open http://127.0.0.1:8501 in your browser. Serve the directory over HTTP; opening index.html directly will not load the dataset.

## Demo in four minutes

1. Overview: 80 accounts, 1,578 events, and 22 accounts flagged under default rules.
2. Open ACC-0001. Switch the timeline to All activity and scroll to October 11. Follow failed logins, password reset, new-device/new-country login, beneficiary addition, and the $6,322 transfer. Switch back to Signals only for the explanation.
3. Add a case note and save it. Notes persist only in the current browser and are scoped to the dataset.
4. Open ACC-0013 (search the account or advance the queue). Reveal the synthetic ground truth to show benign travel.
5. In Detection playground, raise the account alert threshold from 40 to 70. Alerts drop from 22 to 8; false positives drop from 14 to 0; recall stays 8/12 (66.7%). This is an engineered example, not a production benchmark.
6. In Investigate accounts, choose All accounts and search ACC-0009. Its low-signal takeover is missed by these rules.
7. Show CSV upload and download, then describe the development workflow and limitations.

## Features

- Four views: overview, account investigation, detection playground, data and methodology.
- Global date, home-country, and account-search filters.
- Explainable event scoring using only historical activity.
- Account-level precision, recall, and confusion matrix when labels exist.
- Baseline-versus-current rule comparison.
- Searchable and paginated alert queue, event timelines, case outcomes and notes.
- CSV validation, import, alert/timeline/data export, and JSON case-note export.
- Responsive layout with horizontally scrollable data tables on small screens.
- Analysis and uploads stay in the browser; no external AI API, database, or API key required.

## Dataset

`dist/data/events.csv` and `events.json` are generated by `scripts/generate_data.py` with seed 42 using only the Python standard library. The 80 accounts are entirely fictional. IPs are documentation addresses, not customer IPs. All amounts are USD.

```bash
python3 scripts/generate_data.py
```

Scenarios: 8 strong-signal takeovers, 4 low-signal takeovers, 8 legitimate travelers, 6 legitimate password recoveries, 6 new phones, and 48 routine accounts. Activity spans October 1–11, 2026 UTC.

CSV fields: `event_id`, `account_id`, `timestamp`, `event_type`, `device_id`, `country`, `ip_address`, `amount`, `beneficiary_id`. Optional: `is_ato` (consistent 0/1 label per account), `scenario`. See the app's Data & methodology view for validation details. Limit: 50,000 events / 10 MB.

## Detection semantics

New device and new country each add 20 at a successful login. A preceding failed-login burst adds 25; a recent password reset adds 15. A large transfer after a suspicious login on the same device adds 45; a large transfer to a recently added beneficiary adds 35. Rules use configurable time and amount thresholds.

Reasons on an event add together; account score is the highest event score, capped at 100. The first successful login establishes an initial baseline. New-device/new-country comparisons use previously successful logins. Same-timestamp events use event ID order. Labels and scenario descriptions are never scoring inputs.

An account alerts if its score reaches the account threshold. A suspicious login for the transfer rule uses that same threshold. A high threshold can therefore affect transfer-rule eligibility as well as account alerting. The app exposes rule reasons; score is not a probability.

Date filters select accounts with any activity in the UTC interval. Country selects an account's first-successful-login country (first event if there is no successful login). Rules, evaluation metrics, exposure, and account timelines use full available account history. Only the daily chart truncates events to the selected dates. This is a cohort investigation tool, not a period-loss report.

Flagged transfer value means the sum of transfer events whose event score meets the alert threshold. It is not confirmed fraud loss. Ground-truth labels apply to accounts, including benign pre-attack activity. Metrics exclude unlabeled accounts and display N/A when their denominator is zero.

## Validation

Node.js 20+ is required only for the dependency-free engine tests:

```bash
node --test tests/*.test.mjs
```

Nine tests cover expected outcomes, rule-threshold effects, label independence, future-context exclusion, expired lookbacks, absent labels, CSV quoting, invalid uploads, and export formula escaping.

`submission/browser-checks.json` records the browser interaction checks. `scripts/browser_qa.mjs` is the development QA helper; its Playwright import and Chrome location are specific to the authoring environment. To repeat browser QA elsewhere, install Playwright in your environment and adapt those two paths. They are not app runtime dependencies.

## Limitations

This is a synthetic educational prototype. It is not a trained model or a production fraud control. The rules deliberately miss attacks without unusual observable behavior and can flag benign changes. It does not infer geographic travel speed, enforce MFA, stop transactions, or contact customers. Uploading activity does not persist it across reloads. Rule settings reset on reload. Notes persist in browser local storage, without authentication, server backup, or multi-user case management.
